# Эксплуатация

Все примеры ниже относятся к пользовательской службе `vacancy-bot.service` из README и выполняются её владельцем. Они не управляют какой-либо существующей персональной установкой автора.

## Проверка

```bash
systemctl --user status vacancy-bot.service --no-pager
journalctl --user -u vacancy-bot.service -n 100 --no-pager
python3 -m jobbot.status --database "$HOME/.local/state/vacancy-bot/live.sqlite"
```

`status` systemd показывает процесс, `journalctl` — последние события, `jobbot.status` открывает БД только для чтения и выводит целостность, режим, причину остановки, размеры очередей и ошибки источников. Он не доказывает, что процесс работает прямо сейчас. Отсутствующая БД не создаётся этой командой.

События журнала: `started`, `source_checked`, `source_error`, `model_review`, `application_packet`, `delivery`, `stopped_with_error`. Результат `card_sent` означает, что карточка подтверждена, а файл ещё ожидает своего этапа. `sent` завершает нужные этапы. Ошибки HTTP не выводят URL с токеном или произвольное описание Telegram.

## Частые ситуации

| Симптом | Что проверить |
|---|---|
| Нет сообщений сразу после установки | Первый снимок не рассылается. Ждите нового поста, проверьте роли и `source_checked`. |
| Не найден канал | Точное имя без `@`, доступность `t.me/s/<name>`, интернет и ошибки источника. |
| Пропускается подходящее название | Добавьте буквальный вариант/перевод в `target_roles`. Изменение настройки не переигрывает уже неизменные старые посты. |
| Лишние карточки | Сузьте роли и отключите `allow_keyword_only`; посмотрите основной заголовок, а не только упоминание инструмента. |
| Очередь модели растёт | Проверьте локальную Ollama и ресурсы; роли/письма включаются разными флагами. Явные цели могут идти по правилам, неоднозначные ждут. |
| Карточка задерживается при включённых письмах | Она отправляется только после готовности TXT; модель может работать несколько минут. |
| `wrong_bot`, `webhook_exists` | Проверьте имя своего бота и эксклюзивность. Настройщик не удаляет webhook автоматически. |
| Credentials требуют `0600` | Исправьте права на принадлежащий вам файл через `chmod 600 ПУТЬ`; не печатайте его содержимое в чат. |
| `delivery_halted` или `uncertain` | Остановите службу и сравните очередь с реальным чатом; не повторяйте отправку вслепую. |
| Служба не стартует после выхода из SSH | Проверьте `loginctl show-user "$USER" -p Linger` и выполнение `enable-linger` для правильного пользователя. |

## Неопределённая доставка

При таймауте Telegram мог принять сообщение, даже если ответ не дошёл. Для такой записи повтор автоматически запрещён. Остановите службу, сохраните резервную копию и выясните с владельцем, есть ли карточка и файл в чате.

`outbox.message_id` хранит подтверждённую карточку. Если ID есть, нельзя сбрасывать его при повторе файла. Если подтверждённое сообщение существует, восстановление должно отразить именно этот факт и его реальный ID. Если доказано, что отправки не было, владелец может разрешить повтор **конкретного этапа**. Если выяснить результат нельзя, оставьте запись пропущенной/неопределённой и не имитируйте успешную доставку.

Универсальная кнопка «снять все ограничения» намеренно не предоставляется: конкретное восстановление зависит от двух этапов и фактического чата. Правки БД допустимы только после остановки процесса, резервной копии и проверки соответствующей записи; глобальное удаление `delivery_halted` само по себе проблему не решает.

## Резервная копия SQLite

SQLite backup API учитывает WAL. Пример создаёт новую копию с отметкой UTC в пользовательском каталоге состояния:

```bash
umask 077
python3 - <<'PY'
from datetime import datetime, timezone
from pathlib import Path
import sqlite3

root = Path.home() / '.local/state/vacancy-bot'
source = root / 'live.sqlite'
destination = root / ('backup-' + datetime.now(timezone.utc).strftime('%Y%m%dT%H%M%S%fZ') + '.sqlite')
with sqlite3.connect(source.as_uri() + '?mode=ro', uri=True) as src:
    with sqlite3.connect(destination) as dst:
        src.backup(dst)
print(destination)
PY
```

`umask 077` ограничивает права новых файлов; `mode=ro` не даёт создать отсутствующую исходную БД. Резервная копия содержит личные тексты и письма, поэтому её нельзя коммитить. Credentials и профиль сохраняются отдельно в приватном месте, с такими же ограниченными правами. Код восстанавливается из Git.

Восстановление снимка не возвращает Telegram назад во времени. Если после копии были реальные отправки, старые `pending` из восстановленной БД способны привести к дублям: сначала сопоставьте их с чатом. Это не процедура «просто заменить файл».

## Обновление кода

1. Остановите свою службу: `systemctl --user stop vacancy-bot.service`.
2. Сделайте резервную копию и сохраните используемый commit через `git rev-parse HEAD`.
3. Проверьте `git status`, затем получите обновление через `git pull --ff-only`. Флаг `--ff-only` откажется от автоматического merge при разошедшейся локальной истории.
4. Выполните тесты. Сравните свою конфигурацию с новым примером: шаблон не должен перезаписывать локальные настройки и профиль.
5. Если меняли unit, установите его копию и выполните `systemctl --user daemon-reload`.
6. Запустите `systemctl --user start vacancy-bot.service`, проверьте журнал и read-only статус.

Обновление создаёт недостающие таблицы/колонки, но не переотправляет исходный снимок. Не используйте существующую чужую БД для новой личной установки. Откат кода после изменения схемы требует отдельной проверки совместимости и учёта уже отправленных сообщений.

## Что не хранить в Git

Настоящие TOML, credentials, профиль, исходные CV, БД/WAL/SHM, письма, дампы постов и журналы. `.gitignore` уменьшает риск случайного добавления, но не удаляет ранее отслеживаемые файлы и не заменяет просмотр `git diff --cached`. Если токен всё-таки опубликован, его нужно отозвать в BotFather; удаление текущего файла не удаляет секрет из истории.
